# Web 招聘者端界面审计（2026-08-15）

## 范围

- 视口：1280px 桌面端
- 路径：登录 → Dashboard → 职位列表 → 职位详情/创建 → 申请列表 → 申请详情
- 目标：让招聘者更快判断“现在该处理什么”，并减少开发态信息对业务界面的干扰。

## 总体判断

视觉基础已经统一：青绿色品牌色、卡片圆角、状态标签、表单控件和加载/空/错状态都有共享样式。当前最大的损耗不在“好不好看”，而在信息表达和布局稳定性：内部 UUID、`persisted backend`、`server-managed fields`、`not connected in this slice` 等开发态内容进入正式界面；列表列宽不足导致文字粘连；职位详情缺少预期的双栏布局；申请详情存在乱码与密度失衡。

## 优先级建议

### P0：先修可见缺陷

1. 从业务界面移除内部 UUID、版本号和开发态说明。确有排障需要时放进折叠的“技术信息”区域，并默认隐藏。
2. 修复职位详情布局类名不一致：页面使用 `detail-grid`，样式定义的是 `detail-layout`，导致侧栏掉到主内容下方。
3. 修复申请详情中的 `Â·` 字符编码问题。
4. 重做职位和申请列表列宽：职位类型与地点、职位名与 ID、操作按钮与说明当前会粘连。禁止在单元格中直接展示完整 UUID。
5. 删除每一行都显示的 `DRAFT jobs editable`；只对草稿显示明确的 `Edit` 操作，其他状态按允许动作展示。

### P1：重排信息层级

1. Dashboard 保留 3–4 个需要行动的指标；公司认证状态移到账号/公司区域，不与待办指标并列。
2. 申请列表优先展示候选人、职位、阶段、申请时间、负责人和一个明确主操作。ML 未接入时隐藏整列，避免整列 `Unavailable`。
3. 申请详情采用“候选人/简历为主，决策为辅”的 2 栏结构；压缩无内容时仍保留的 390px 简历卡片高度。
4. 职位详情把业务信息放主区，把状态、负责人、时间和动作放 320–360px 侧栏；发布/暂停/关闭动作固定在侧栏顶部。
5. 把页面文案从实现语言改为任务语言，例如 `4 persisted job postings` → `4 job postings`。

### P1：可访问性与交互

1. 将 9–11px 的辅助文字提升到至少 12–14px，并复核灰色文字与背景的对比度。
2. 顶部导航和纯文字按钮的点击高度提升到约 44px。
3. 申请列表不要把整行做成一个超长可访问名称的按钮；使用语义表格/列表，并给详情动作单独的明确链接。
4. 表单校验失败后把焦点移到第一个错误字段，增加页面级错误摘要，并用 `aria-describedby` 关联字段与错误。当前焦点仍停留在 `Save draft`。
5. 保留已有的文字状态标签，不要只依赖颜色表达 Draft、Active、Interview 等状态。

## 分步骤健康度

1. 登录：良好。品牌与表单分区清楚；应补密码显隐，并避免展示尚未实现的忘记密码入口。
2. Dashboard：良好。结构清楚、近期内容可操作；认证状态不应占用核心指标位。
3. 职位列表：较差。列宽和操作区发生粘连，开发态辅助文案重复出现。
4. 申请列表：较差。内部 UUID 暴露，ML 未接入状态占据整列，整行按钮的可访问名称过长。
5. 申请详情：较差。存在乱码、内部 ID、空白过大和决策区过密。
6. 职位创建：良好。两栏结构和实时预览有效；错误后焦点恢复需要改进。
7. 职位详情：较差。预期双栏未生效，开发字段成为大块主内容，操作与上下文分离。

## 证据限制

本次只检查了 1280px 桌面视口与当前演示数据；未验证移动端重排、浏览器缩放、屏幕阅读器朗读、完整键盘遍历和真实对比度数值，因此不能据此声称满足完整 WCAG 要求。
